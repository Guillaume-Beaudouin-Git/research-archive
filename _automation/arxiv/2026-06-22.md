## Notes techniques

### Blocage réseau arXiv API
Toutes les requêtes vers arxiv.org retournent HTTP 403 depuis l'environnement cloud (arXiv API,
RSS feeds, interface HTML). Cette restriction est la même que lors des scans précédents depuis
juin 2026 ; les scans opérationnels lisent depuis `_staging/` généré par le VPS.

### Absence de staging file pour 2026-06-20
Le dernier fichier de staging disponible est `_staging/2026-06-19.json`, traité lors du scan
du 2026-06-19. Il n'existe pas de `_staging/2026-06-20.json` dans ce dépôt.

La cron VPS `30 6 * * 1-5` (weekdays) aurait dû tourner vendredi 2026-06-20. Deux causes
probables pour l'absence du staging :

1. **TODO patch non appliqué** (cause structurelle documentée dans CLAUDE.md) : `fetch_arxiv.sh`
   pousse du raw XML dans `_automation/arxiv/_raw/` (gitignorés), non des staging JSON. Contrairement
   à `fetch_alpha_sources.sh` (patché 2026-06-10), arxiv ne distille pas les données sur le VPS avant
   push. Les XML raw étant gitignorés, la session cloud ne peut pas exécuter `process_arxiv_raw.py`
   sur de nouvelles données.

2. **Silent fail possible** : `fetch_arxiv.sh` fonctionne sans redirection log (CLAUDE.md : "sans
   redirection log, silent fail"). Un échec silencieux ne serait pas détecté.

### Impact
Les scans de 2026-06-20 (vendredi) et 2026-06-21 / 2026-06-22 (week-end, pas de cron) ne sont
pas disponibles. Estimation : ~5-15 papers non vus (volume journalier habituel q-fin).

### Recommandation
Appliquer à `fetch_arxiv.sh` le même patch que `fetch_alpha_sources.sh` :
1. Sur VPS : `process_arxiv_raw.py` après chaque fetch → génère `_staging/<date>.json`
2. Push git limité à `_staging/` + `_seen/` (comme alpha_hunt)
3. Ajouter redirection log : `>> logs/arxiv_fetch.log 2>&1`

Cela permettrait aux sessions cloud de trouver systématiquement les données du jour.
