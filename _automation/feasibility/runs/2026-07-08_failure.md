## What went wrong this session specifically

Unlike 2026-07-07 (which pre-classified handlers before spending network attempts), this
session ran all 20 items through `orchestrator.py --single` **before** checking whether
`yfinance` was even installed. All 20 completed without a Python exception (`orchestrator.py`
itself never crashed — rc=0 every time) and all 20 returned `FAIL_A`. On the surface this
looked like a clean batch of real statistical rejections. It was not: `yfinance` was missing
for the entire run, so every handler that needs price data (`GenericHandler`/`TESTABLE_GENERIC`,
`RegimeFilterHandler`, `SkipMonthHandler`) silently produced `n_days=0` / `Sharpe=nan` and the
gate logic reported `FAIL` on empty data — the exact "silent infra failure" signature flagged
repeatedly in `digests/2026-06-15.md`, `2026-06-14.md`, and the 2026-07-04/06/07 failure reports.


Both candidate data sources are blocked at the proxy layer in this cloud sandbox (checked
`$HTTPS_PROXY/__agentproxy/status` — neither `query1/query2.finance.yahoo.com` nor

internal ranges). This is identical to the finding in every prior failure report since
2026-06-21 — the block is a structural property of this execution environment, not a transient
outage.

periodically (e.g. weekly, alongside the existing VPS crons in `CLAUDE.md`). Once that file

the data backfill itself must happen from the VPS, not from a future instance of this routine.
